# Stage 10 kickoff

Stage 10 starts directly from the validated Stage 9 `main` baseline.

Baseline commit: `a18a469722377eb797152b48a8f152768673c1ae`

The Stage 9 baseline is frozen before Stage 10 implementation begins.

## Stage 10.1 — feature contract and acceptance criteria

### 1. Feature goal

Stage 10 must introduce one clearly bounded feature that materially extends StochX beyond the completed Stage 9 Box–Jenkins workflow while preserving all existing Stage 8 and Stage 9 public behavior.

Before implementation begins, the Stage 10 feature name, one-sentence goal, scope, and non-goals must be frozen in this document or an explicitly linked Stage 10.1 specification. Stage 10.1 is a contract phase; it does not authorize unrelated refactoring or silent numerical changes.

### 2. Public API boundary

Any new public feature must expose a stable documented function/class or orchestration result under `stochx.<module>` with explicit inputs, deterministic defaults, return type, numerical semantics, and failure behavior.

Existing public APIs remain compatibility boundaries. Stage 10 may compose them but must not silently change signatures, return semantics, numerical definitions, or field meanings.

If structured output is introduced, its public result must make configuration, effective observations, core numerical outputs, status/failure state, and relevant interpretation or rationale auditable. Core numerical arrays must be immutable or otherwise protected from accidental mutation.

### 3. Numerical conventions

Before implementation, Stage 10 must explicitly freeze, where applicable:

- indexing and lag/horizon numbering;
- missing-observation policy and effective observation count;
- numerical precision and test tolerances;
- confidence/significance convention;
- degrees-of-freedom convention;
- ordering and tie-breaking rules;
- transformation and inverse-transformation rules;
- insufficient-data and degenerate-input behavior.

Third-party numerical behavior must not become an undocumented StochX convention. Any inherited convention must be identified explicitly.

### 4. Failure semantics

The feature must fail explicitly for invalid input, insufficient data, invalid configuration, non-finite input, numerical failure, unsupported configuration, or absence of a valid result.

Failures must be documented, diagnostic, and must not silently produce partial success. A failure in one optional candidate/computation must not abort unrelated valid work unless fail-fast semantics are explicitly frozen.

### 5. Compatibility requirements

Stage 8 remains frozen, including its `CorrelogramResult`, AC/PAC, Q-Stat/Prob., DF/model_df, confidence-band, missing-observation, table, interpretation, plotting, and residual-correlogram contracts.

Stage 9 remains compatible, including identification, candidate estimation, residual validation, deterministic selection, forecasting, transformation restoration, auditable metadata, and immutable numerical snapshots.

Any intentional compatibility change requires its own explicit specification and regression evidence and is outside the default Stage 10.1 scope.

### 6. Testing contract

Every Stage 10 feature must add focused regression tests covering normal API usage, defaults and options, numerical outputs, shape/length invariants, invalid inputs, insufficient observations, non-finite inputs, deterministic behavior, and at least one user-facing integration path.

Representative Stage 8 and Stage 9 compatibility tests must remain green.

Numerical parity requirements must use deterministic fixtures documenting source, settings, sample size, expected outputs, and tolerances. Random fixtures must freeze the generator configuration and seed.

### 7. Documentation contract

Stage 10 documentation must distinguish what the user supplies, what StochX computes, what StochX guarantees, and what it does not guarantee.

The Stage 10.1 specification must record the feature goal, scope, non-goals, public API boundary, numerical conventions, failure semantics, compatibility guarantees, testing requirements, fixtures, examples, and acceptance criteria.

### 8. First-commit rule

The first Stage 10 implementation commit must be limited to the Stage 10 specification/scaffold required to establish the feature boundary. It must not modify Stage 8 numerical formulas, Stage 8 public result fields, unrelated modules, or existing tests merely to make them pass.

After the first implementation commit, the focused Stage 10 tests, full local test suite, and existing CI matrix must remain green before advancing to Stage 10.2.

## Working-tree contract

The local checkout must be on `main`, synchronized with `origin/main`, and have no tracked or untracked implementation changes before a Stage 10 implementation commit. Development environment directories such as `.venv/` must remain ignored/untracked.

## Acceptance checklist

- [ ] Stage 10 feature name and one-sentence goal are frozen.

- [ ] Public API boundary is defined.
- [ ] Public result contract is defined where applicable.
- [ ] Numerical conventions are explicit and testable.
- [ ] Missing-observation/effective-observation rules are explicit.
- [ ] Failure semantics are explicit and testable.
- [ ] Stage 8 numerical/API contracts are explicitly frozen.
- [ ] Stage 9 public behavior is explicitly preserved.
- [ ] Numerical fixture requirements are defined.
- [ ] Focused, integration, and compatibility test requirements are defined.
- [ ] Documentation requirements are defined.
- [ ] The first Stage 10 commit is restricted to specification/scaffold work.
- [ ] `stage-9-freeze` remains unchanged.
- [ ] Full local validation and CI are required before Stage 10.2.

## Stage 10.1 completion gate

```text
FEATURE GOAL FROZEN
        +
PUBLIC API FROZEN
        +
NUMERICAL CONVENTIONS FROZEN
        +
FAILURE SEMANTICS FROZEN
        +
STAGE 8/9 COMPATIBILITY FROZEN
        +
ACCEPTANCE TESTS DEFINED
        ↓
✅ STAGE 10.1 FROZEN
```

No substantive Stage 10 implementation should begin until this gate is satisfied.

## First-commit workflow

1. Synchronize and verify `main`.
2. Verify `stage-9-freeze` points to `a18a469722377eb797152b48a8f152768673c1ae`.
3. Run the full baseline test suite.
4. Commit the Stage 10.1 specification/scaffold.
5. Verify the commit is green through the complete CI matrix.
6. Begin Stage 10.2 only after the gate is satisfied.

No Stage 8 numerical/API contract may be changed implicitly by Stage 10 kickoff work.
