# Stage 10 kickoff

Stage 10 starts directly from the validated Stage 9 `main` baseline.

Baseline commit: `a18a469722377eb797152b48a8f152768673c1ae`

The Stage 9 baseline is frozen before Stage 10 implementation begins.

## Stage 10.1 — feature contract and acceptance criteria

### 1. Feature goal

Stage 10 feature: **linear-Gaussian state-space modeling with a deterministic Kalman-filter core**.

Goal: provide a small, auditable state-space API that lets users specify a time-invariant linear-Gaussian transition/measurement system and obtain filtered states, covariances, innovations, effective observation counts, and Gaussian innovation log likelihood, while preserving all existing Stage 8 and Stage 9 behavior.

Scope is deliberately limited to the core filtering layer in Stage 10.2. Parameter estimation, smoothing, nonlinear state-space models, time-varying system matrices, control inputs, and probabilistic forecast calibration are out of scope for Stage 10.2 unless explicitly specified by a later stage.

### 2. Public API boundary

The Stage 10.2 public boundary is:

```python
from stochx.timeseries import LinearStateSpace, KalmanFilterResult, kalman_filter, local_level_filter
```

`LinearStateSpace` defines the transition/observation system and initial state/covariance. `kalman_filter()` performs deterministic filtering. `local_level_filter()` provides a documented scalar convenience model. `KalmanFilterResult` is the auditable immutable result object.

Any new public Stage 10 feature must expose a stable documented function/class or orchestration result under `stochx.<module>` with explicit inputs, deterministic defaults, return type, numerical semantics, and failure behavior.

Existing public APIs remain compatibility boundaries. Stage 10 may compose them but must not silently change signatures, return semantics, numerical definitions, or field meanings.

### 3. Numerical conventions

For Stage 10.2, the state-space convention is:

- `x_t = F x_(t-1) + w_t`;
- `y_t = H x_t + v_t`;
- `w_t ~ N(0, Q)`;
- `v_t ~ N(0, R)`;
- initialization is explicit through `initial_state` and `initial_cov` for the general API;
- local-level initialization uses the first finite observation when available and a documented diffuse-like variance when process variance is positive;
- covariance matrices are symmetrized after propagation and Joseph-form updates;
- innovation likelihood uses a Cholesky factorization, with minimal numerical jitter only when the innovation covariance is numerically singular;
- NaNs are treated as missing observations per dimension;
- an all-missing time row performs prediction only and contributes no likelihood increment;
- `nobs` counts time rows;
- `effective_nobs` counts observed scalar measurements;
- `missing_observations` counts missing scalar measurements;
- infinite observations and non-finite model matrices are rejected;
- core numerical arrays are immutable in `KalmanFilterResult`.

Third-party numerical behavior must not become an undocumented StochX convention.

### 4. Failure semantics

The feature must fail explicitly for invalid input, insufficient data, invalid configuration, non-finite input, numerical failure, unsupported configuration, or absence of a valid result.

The Stage 10.2 core raises `ValueError` for incompatible matrix shapes, non-square transition matrices, non-finite model specifications, negative-definite covariance matrices, empty observations, infinite observations, and unsupported non-empty control matrices.

Failures must be documented, diagnostic, and must not silently produce partial success.

### 5. Compatibility requirements

Stage 8 remains frozen, including its `CorrelogramResult`, AC/PAC, Q-Stat/Prob., DF/model_df, confidence-band, missing-observation, table, interpretation, plotting, and residual-correlogram contracts.

Stage 9 remains compatible, including identification, candidate estimation, residual validation, deterministic selection, forecasting, transformation restoration, auditable metadata, and immutable numerical snapshots.

Stage 10.2 is additive and does not modify those contracts.

### 6. Testing contract

Stage 10.2 tests cover deterministic scalar reference values, multivariate filtering, partial and full missing observations, deterministic repeatability, immutable result arrays, invalid matrix/covariance specifications, infinite/empty observations, and public-result aliases.

Representative Stage 8 and Stage 9 compatibility tests must remain green.

### 7. Documentation contract

Stage 10 documentation must distinguish what the user supplies, what StochX computes, what StochX guarantees, and what it does not guarantee.

The detailed Stage 10.2 contract is documented in `docs/stage10/10.2_state_space_kalman.md`.

### 8. First-commit rule

The first substantive Stage 10 implementation commit is limited to the state-space/Kalman core, its public exports, focused tests, and documentation. It must not modify Stage 8 numerical formulas, Stage 8 public result fields, unrelated modules, or existing tests merely to make them pass.

## Working-tree contract

The local checkout must be on `main`, synchronized with `origin/main`, and have no tracked or untracked implementation changes before a Stage 10 implementation commit. Development environment directories such as `.venv/` must remain ignored/untracked.
