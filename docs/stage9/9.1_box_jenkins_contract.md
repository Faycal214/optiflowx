# Stage 9.1 — Box–Jenkins Workflow Contract

**Branch:** `stage-9-box-jenkins`  
**Baseline:** Stage 8 frozen commit `31806c2ee25c7ab8e89f1549e5bd59040a65179e`

## 1. Purpose and scope

Stage 9 implements the course-faithful Box–Jenkins workflow around the existing StochX time-series primitives. The workflow is strictly sequential:

1. identify a suitable stochastic representation and candidate orders;
2. estimate candidate models;
3. validate residuals and reject inadequate specifications;
4. select the preferred adequate model using frozen information criteria and diagnostic rules;
5. forecast from the selected model;
6. expose all decisions through one auditable public result object.

Stage 9 must not modify the frozen Stage 8 numerical or public `CorrelogramResult` contract. In particular, Stage 9 may consume the Stage 8 correlogram, Ljung–Box statistics, confidence bands, aliases, and residual-correlogram APIs, but may not redefine them.

## 2. Frozen workflow order

The public workflow is ordered and explicit:

```text
raw series
   ↓
data validity / transformations
   ↓
identification
   ↓
candidate model set
   ↓
estimation
   ↓
residual validation
   ↓
adequate candidate set
   ↓
model selection
   ↓
final fitted model
   ↓
forecasting
```

A later step must not silently perform an earlier step with different conventions. Every automatic shortcut must expose its assumptions in the returned result.

## 3. Identification contract

### 3.1 Input

Identification accepts a finite univariate series together with optional transformation metadata and a requested maximum lag.

Required validation:

- at least two usable observations after the series' existing missing-value policy;
- no infinite observations;
- deterministic, documented treatment of missing observations;
- the original series and transformed series remain distinguishable in the result.

### 3.2 Identification outputs

The identification result must preserve or expose:

- effective observation count;
- transformation/differencing applied;
- ACF values and lags;
- PACF values and lags;
- confidence-band information inherited from the Stage 8 conventions;
- candidate AR/MA interpretations derived from ACF/PACF patterns;
- the candidate `(p,d,q)` orders considered or recommended;
- any seasonal candidate information when seasonal identification is explicitly requested;
- auditable reasoning text that points to the observed ACF/PACF pattern rather than presenting an unsupported model choice.

Identification is **candidate generation**, not final model selection.

### 3.3 Identification acceptance criteria

A Stage 9.1 implementation passes identification when:

- the returned lag indexing is deterministic and consistent with StochX correlation results;
- ACF/PACF are obtained through the existing public numerical primitives rather than duplicated formulas;
- the candidate order set is reproducible for the same input and settings;
- no candidate is called “selected” before estimation and residual validation;
- candidate-order evidence is inspectable through the public result.

## 4. Estimation contract

### 4.1 Supported candidate families

The initial Stage 9 workflow must support the existing model families already exposed by StochX:

- AR(p);
- MA(q);
- ARMA(p,q);
- ARIMA(p,d,q);
- SARIMA only when seasonal structure is explicitly enabled by the caller.

The workflow must reuse the existing model estimators instead of introducing a second estimation API.

### 4.2 Estimation outputs

Each estimated candidate must expose or make available:

- model order `(p,d,q)`;
- seasonal order when applicable;
- coefficient estimates;
- standard errors;
- t-statistics;
- p-values;
- log likelihood;
- SIGMASQ or equivalent residual variance estimate when available from the estimator;
- AIC;
- SC/BIC;
- HQ;
- AR roots and MA roots when applicable;
- convergence/estimation status;
- estimation sample size;
- residual series.

### 4.3 Estimation acceptance criteria

For a fixed input and settings, repeated estimation must return numerically stable results within the field-specific tolerances defined by the model-family regression fixtures.

No candidate may be treated as valid if estimation fails, does not converge according to the estimator's documented status, or produces non-finite required model statistics.

## 5. Residual-validation contract

Residual validation is mandatory for every candidate that reaches the selection stage.

### 5.1 Required diagnostics

At minimum, the validation layer must evaluate:

- residual mean/zero-mean diagnostic when supported;
- residual serial-correlation diagnostics;
- the frozen Stage 8 residual correlogram;
- Ljung–Box Q-Stat and Prob. at the configured lags;
- residual normality diagnostics already exposed by StochX when requested by the workflow;
- heteroskedasticity/ARCH diagnostics when requested by the workflow.

### 5.2 Primary adequacy rule

A candidate is **serially adequate** only if the configured residual Ljung–Box checks do not reject the no-autocorrelation null at the configured significance level for all required validation lags.

A candidate with significant residual autocorrelation at a required validation lag is inadequate and must not be selected merely because it has a lower AIC/BIC/HQ.

### 5.3 Residual-correlogram preservation

Residual validation must use the frozen Stage 8 contract, including:

- `model_df` adjustment;
- `DF = lag - model_df`;
- undefined probabilities for non-positive adjusted DF;
- frozen confidence bands;
- immutable numerical arrays;
- ordinary/residual table and alias semantics.

### 5.4 Validation acceptance criteria

A candidate validation result must make it possible to answer:

- which residual diagnostics were run;
- at which lags;
- which null hypotheses were tested;
- which diagnostics rejected or failed to reject;
- whether the candidate is adequate;
- why it is or is not eligible for model selection.

No silent “best model” selection is permitted when all candidates are inadequate.

## 6. Model-selection contract

### 6.1 Eligibility

Only estimated candidates that pass the configured adequacy rules are eligible for final selection.

If no candidate is adequate, the workflow must return an explicit `no_adequate_model` outcome rather than selecting the numerically smallest information criterion by force.

### 6.2 Selection hierarchy

The default selection hierarchy is:

1. residual adequacy;
2. parsimony / model-order preference when statistically equivalent;
3. information criteria among adequate candidates.

The default information criteria exposed to the caller are:

- AIC;
- SC/BIC;
- HQ.

The selection criterion must be explicit. The implementation must not silently alternate between AIC, BIC/SC, or HQ.

### 6.3 Deterministic tie handling

Ties within the configured numerical tolerance must be resolved deterministically using the documented parsimony rule. The same candidate set and settings must always return the same selected model.

### 6.4 Selection acceptance criteria

A selected model must satisfy:

- successful estimation;
- all mandatory adequacy checks;
- finite selection statistics;
- reproducible order and criterion ranking;
- an auditable selection reason containing the winning order and comparison metric.

## 7. Forecasting contract

### 7.1 Input

Forecasting operates only on the final selected adequate model.

The workflow must support:

- configurable forecast horizon `h >= 1`;
- point forecasts;
- prediction intervals at configurable `alpha`;
- restoration to the original scale when differencing or transformations were applied by the workflow.

### 7.2 Forecast outputs

The forecast result must expose:

- forecast horizon/index;
- point forecast;
- lower bound;
- upper bound;
- confidence level / alpha;
- model order;
- transformation metadata required to interpret the scale;
- whether forecasts are on the transformed or restored original scale.

### 7.3 Forecasting acceptance criteria

For fixed model, data, horizon, and alpha:

- forecast values are deterministic within numerical tolerance;
- interval bounds are ordered `lower <= forecast <= upper` whenever finite;
- the forecast index is contiguous and correctly aligned to the requested horizon;
- restored forecasts are numerically consistent with the inverse transformation.

## 8. Public API boundary

Stage 9 must add one orchestration-level public API without replacing the existing low-level APIs.

The preferred boundary is:

```python
from stochx.timeseries import box_jenkins

workflow = box_jenkins(
    y,
    *,
    d=None,
    candidate_orders=None,
    max_p=2,
    max_q=2,
    lags=12,
    selection="aic",
    alpha=0.05,
    forecast_horizon=0,
)
```

The exact keyword set may be refined during implementation, but the following semantics are mandatory:

- input series is explicit;
- differencing/order assumptions are explicit;
- candidate search bounds or candidate orders are explicit;
- residual-validation lag configuration is explicit;
- selection criterion is explicit;
- significance level is explicit;
- forecast horizon is explicit;
- automatic identification must be opt-in or clearly distinguishable from explicit candidate-order input.

### 8.1 Result boundary

The public orchestration result must expose, directly or through stable properties:

```text
input / transformation metadata
identification result
candidate models
residual validation results
eligible models
selection result
selected model
forecast result (when requested)
interpretation / audit text
```

The result must be immutable or otherwise protected against accidental mutation of its core numerical arrays, following the Stage 8 result-design principle.

### 8.2 Low-level API compatibility

The existing public APIs remain valid:

```text
identify()
grid_search()
estimate()
fit_ar()
fit_ma()
fit_arma()
fit_arima()
fit_sarima()
TSResult.diagnostics()
TSResult.residual_correlogram()
correlogram()
```

Stage 9 must compose these APIs rather than silently redefining their numerical behavior.

## 9. Failure semantics

The workflow must fail explicitly and diagnostically for:

- insufficient observations;
- invalid model orders;
- invalid forecast horizon;
- estimation failure for every candidate;
- no adequate candidate after residual validation;
- impossible restoration of transformed forecasts;
- non-finite mandatory statistics.

Partial failure of one candidate must not abort the entire candidate search unless the caller explicitly requests fail-fast behavior.

## 10. Numerical and reproducibility contract

Stage 9 must preserve the existing EViews-parity work wherever fixtures already exist.

Required principles:

- no untracked dependence on random seeds for deterministic estimation;
- candidate ordering is deterministic;
- selection ranking is deterministic;
- field-specific tolerances are used in numerical regression tests;
- all Stage 8 numerical APIs remain untouched;
- any new EViews numerical fixture must record source, settings, sample, and expected precision.

## 11. Stage 9.1 acceptance checklist

Stage 9.1 is complete only when all of the following are true:

- [ ] The workflow order is documented exactly as identification → estimation → validation → selection → forecasting.
- [ ] Identification is explicitly candidate generation, not model selection.
- [ ] Candidate eligibility depends on residual adequacy before information-criterion ranking.
- [ ] The default model-selection criterion is explicit and configurable.
- [ ] A no-adequate-model outcome is explicit.
- [ ] Forecasting is performed only from the selected adequate model.
- [ ] The public orchestration API and result boundary are specified.
- [ ] Existing low-level APIs remain compatibility boundaries.
- [ ] Stage 8 `CorrelogramResult` and related numerical contracts are declared frozen and read-only from Stage 9.
- [ ] Failure semantics and deterministic tie-breaking are defined.
- [ ] Numerical regression fixtures are required for all newly parity-sensitive outputs.
- [ ] Focused Stage 9.1 documentation/tests can verify the contract without requiring implementation of later Stage 9 steps.

## 12. Non-goals for Stage 9.1

Stage 9.1 does not implement:

- a new AR/MA/ARMA likelihood engine;
- new ACF/PACF mathematics;
- new Ljung–Box mathematics;
- new Stage 8 plotting or formatting;
- automatic seasonal model discovery unless explicitly added later;
- machine-learning model selection;
- probabilistic forecast calibration beyond the existing forecasting API.

The purpose of Stage 9.1 is to make the Box–Jenkins orchestration contract testable before any workflow implementation is allowed to redefine conventions.
