# Stage 12.1 — Release-Readiness and Public-Surface Audit

Stage 12 is the productization phase after the frozen Stage 8–11 feature work. The goal is to make StochX a coherent, installable, documented, reproducible release without changing frozen numerical or public API contracts.

## Current baseline

- Package version: `0.2.0`.
- Python requirement: `>=3.10`.
- Version is single-sourced from `stochx/__init__.py` and consumed by Hatchling.
- Build backend: Hatchling.
- Release checks already include distribution building and Twine metadata validation.
- PyPI publishing is prepared through a tag-based workflow but still depends on the repository's trusted-publisher configuration.

## Stage 12 sequence

### 12.1 Public-surface audit

Freeze the intended public import boundaries, metadata identity, version source, compatibility guarantees, documentation entry points, and release acceptance checklist.

### 12.2 Distribution hardening

Build sdist/wheel artifacts, inspect metadata and included files, run `twine check`, and verify clean installation from the built wheel in an isolated environment.

### 12.3 Documentation and example closure

Audit every public StochX and time-series API page, runnable example, Stage 8–11 workflow page, and cross-link. Ensure documentation describes the current API rather than historical implementation details.

### 12.4 CI/release workflow hardening

Verify Python 3.10/3.11/3.12 CI, examples, documentation build/deploy, distribution validation, and tag-triggered release behavior. No release workflow should publish from an unvalidated commit.

### 12.5 Changelog and migration guide

Document the accumulated 0.3-era feature surface and provide a concise migration/compatibility guide for users upgrading from 0.2.x.

### 12.6 Release candidate

Choose the next semantic version only after the package, tests, docs, examples, and release workflow are green. Build immutable candidate artifacts and record their hashes.

### 12.7 Stable release decision

A stable `1.0.0` release is optional rather than automatic. It requires an explicit decision that the public API and numerical contracts are mature enough for compatibility guarantees.

### 12.8 Final release freeze

Freeze the release commit, create a permanent release tag, verify the published artifacts, and record the exact SHA/tag as the project release baseline.

## Acceptance criteria for Stage 12.1

- [ ] Public top-level imports remain `stochx`, `stochx.stochastic`, and `stochx.timeseries`.
- [ ] Frozen Stage 8, Stage 9, Stage 10, and Stage 11 APIs are explicitly treated as compatibility boundaries.
- [ ] Package version remains single-sourced.
- [ ] `pyproject.toml` remains the authoritative build configuration.
- [ ] Supported Python versions remain 3.10, 3.11, and 3.12.
- [ ] Current package metadata is internally consistent.
- [ ] Changelog and citation metadata are identified as release surfaces.
- [ ] Distribution build and Twine validation are required release gates.
- [ ] A release cannot be produced from a failing or unverified commit.
- [ ] No feature code is changed merely to satisfy release plumbing.
- [ ] Stage 12.2 may begin after the full local test suite and CI are green.

## Non-goals

Stage 12.1 does not:

- bump the package version;
- create a `1.0.0` release;
- change frozen numerical formulas;
- remove or rename public APIs;
- publish to PyPI;
- alter Stage 8–11 behavior.
